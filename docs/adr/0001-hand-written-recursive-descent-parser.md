# 手写递归下降解析器，否决解析器生成器

参考实现（docs/promql，Prometheus 3.x 时代快照）用 goyacc 生成 LALR(1) 解析器（~18 个非终结符、~1440 个状态、11 层优先级声明）。我们决定在 Java 中**手写递归下降 + 优先级爬升**，不做 yacc 文法的生成器移植（byaccj / jflex+CUP 均否决）。

理由：① 多错误累积模型（对齐 Go 的 ParseErr 列表行为）在 CUP 类生成器中是最弱项，Go 靠 action 内 panic + yacc error 产生式实现，难以在生成表上忠实复刻；② 零运行时依赖自然满足（无需引入生成器 runtime 或提交生成代码）；③ 可用普通调试器单步，yacc 表不可调试；④ 文法为表达式文法，是递归下降的甜区，11 层优先级用一张优先级表处理。词法器上下文敏感（`fill(` 关键字判定、括号内时长表达式、子查询冒号消歧），无论选哪条路都必须手写移植，生成器路线并不能省掉这部分。

## Consequences

- 与上游 yacc 文法存在漂移风险。缓解：移植 Go `parse_test.go` 全量用例作为 conformance 金标准，任何行为分歧以快照源码为准。
- 上游文法变更时，升级 = 人工对照快照重新移植，无法机械 diff 生成表。
